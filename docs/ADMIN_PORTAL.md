# Court administrator portal

The `/admin` dashboard uses the existing, normalized court registry and Supabase password sign-in. A selected court is never an authorization grant: every protected API request verifies the signed-in identity, an active staff membership, the selected court, and the identity's court-specific alias.

The dashboard follows the supplied admin portal mockup with responsive navigation, court context, licensed/assigned/available seats, participant creation, searchable accounts, credential resets, activity, and settings. Counts and subscription status come from the database. Test courts are labeled; no mock participants or manufactured activity ship in production.

## Working flows

- **Create Account:** enter a globally unique 3–32 character participant username. The internal Auth alias is previewed using the same helper as participant sign-in. The existing server creates the Auth identity, atomically assigns a court seat, and records the creation. A server-generated temporary password is shown once; no staff-selected or default password is introduced.
- **Credential handoff:** reveal or copy credentials explicitly. The card clears on dismissal, court/account change, sign-out, relevant navigation, and after five minutes. Secrets remain in component memory and never enter local storage, URL parameters, audit responses, or application logs. The participant's first sign-in still requires a password change.
- **Participants:** search by username and filter assigned, active, suspended, removed, or all accounts. Suspension retains a seat; removing an assignment frees it and retains records; restoration checks capacity. Every account action requires an explicit confirmation dialog. Created-by labels distinguish the current administrator from other court staff without exposing unrelated identities.
- **Activity:** authenticated, court-scoped audit events with validated timestamp/UUID cursor pagination. Participant names are resolved only inside the same court. Refresh and older-event controls read persisted events; passwords and participant-owned private content are excluded.
- **Settings:** authoritative court/subscription details, court selection, password change with current-password verification, and sign-out. Licensing and staff grants remain owner-managed.

Delayed requests are ignored after a court or account change, including account provisioning responses containing temporary credentials. Errors do not display a success card or manufacture database state.

## Verification and limits

Run `npm test`, `npm run test:db`, `npm run typecheck`, `npm run lint`, `npm run security:scan`, and `npm run test:browser:production -- admin-portal.spec.ts`. The browser harness uses fictional accounts and simulated HTTP responses; it verifies UI behavior, not production Auth delivery. Database tests run the actual migrations against disposable PostgreSQL with different roles and courts. Hosted checks must additionally use a genuine court administrator session; never replace hosted authorization with the harness.

This release needs no database migration and does not change existing participant creation, reset, suspension, removal, or first-use password semantics. Existing JWT expiry and offline-cache limitations still apply; removal is not an instant remote wipe. The portal remains access administration and cannot read participant schedules, medication records, notes, finances, or attendance. It is not a compliance certification or a court case-management system.

## Separate owner dashboard

`/owner` is the program owner's dashboard. `/admin` remains the court staff portal. A link in the court portal opens the owner page, but access always requires the server-owned boolean `app_metadata.daybridge_platform_owner=true` on an existing verified Supabase Auth account. No account is automatically promoted, and this role cannot be granted through the public application, user-editable metadata, a court staff membership, or a request field. A trusted operator assigns the initial owner through the Supabase Auth Admin API after the owner identifies the intended account; preserve all existing app metadata. Revoking that flag blocks subsequent owner operations immediately.

Owners can create or reuse states and circuits, create courts, set seat limits, publish/unpublish directory entries, pause enrollment, enable/disable the staff portal, and assign/revoke verified existing staff logins. New courts default to a private, clearly labeled test court with 25 free-pilot seats. Creating a court does not automatically provision staff accounts, charge money, or enroll participants. Use the court’s New staff login control to create individual staff accounts afterward. Real courts must be intentionally marked as real and published when ready.

State/circuit/court sign-in codes are immutable in this UI so existing aliases keep working. Court display names can change. Occupied seats are counted in PostgreSQL without REST row-limit truncation; active and suspended participants both count. Seat reductions lock the same court row as participant assignment and cannot go below occupied seats. Existing participant data is retained when a court is paused or its portal is disabled.

Staff setup previews the exact `username@state.circuit.court` alias. **New staff login** creates a confirmed Auth identity with a cryptographically generated temporary password and assigns the selected court role. **Link existing login** remains available for a confirmed identity previously prepared in Supabase. Neither path accepts participant or owner identities. A court can have multiple staff accounts; staff do not consume participant seats. Each grant, reset, revocation and restoration requires confirmation and appends an audit event. Court staff cannot invoke owner setup, inspect the owner Auth directory, or promote themselves.

The additive `owner_court_setup` migration installs service-only RPCs and narrowly scoped private Auth lookup helpers. It seeds no accounts, roles, courts, memberships, or participant data. Owner HTTP APIs verify the signed session and current Auth record; the database rechecks the owner flag for each operation. Owner API responses use `private, no-store`; the existing service worker does not cache `/api` or `/owner` navigation. This dashboard does not display participant schedules, medication records, budgets, notes, attendance, or snapshots.

Verification includes input validation, disposable PostgreSQL tests for owner revocation, non-owner denial, forged roles, atomic hierarchy creation, staff alias checks and seat limits, plus desktop/mobile browser fixtures for creation, confirmation, staff assignment/revocation and signed-out response handling. Fixtures are UI evidence only. Production activation still requires choosing the real owner account and verifying its signed-in owner flow; no permission is assigned merely by shipping the dashboard.

## Using the owner dashboard

- **Overview** shows database-backed court totals, active staff assignments, assigned participant seats, remaining capacity, configuration issues, and the eight most recent persisted owner setup events. Configuration badges do not certify pilot readiness.
- **Courts** searches by court, circuit, or state and filters missing staff, paused portals, and test courts. Open a court to update settings or manage staff; use **Add a court** to start a new 25-seat free pilot.
- **Staff & access** lists active court assignments, with an option to include revoked assignments. Assignment management opens the relevant court, whose staff history always includes active and revoked accounts; it never grants owner permission.
- **Setup guide** explains the complete sequence: register a private court, create individual staff logins, privately hand off temporary credentials, verify access and publish, then onboard a small participant group. It also explains every setting and the immutable sign-in codes.
- **Security & account** explains current authorization checks and privacy boundaries, identifies the server-verified owner session, and provides password change with current-password verification.

Navigation to the guide retains draft form fields. Refresh, switching edited courts, leaving the dashboard, and sign-out ask before discarding unsaved setup fields. Owner activity responses contain only action, court display name, identifier, and time; they exclude Auth credentials, participant records, and audit payloads. This dashboard enhancement requires no new schema or permission grants.

Owner MFA is not currently required. The internal sign-in alias is not a mailbox, so email recovery cannot deliver there; retain trusted Supabase project administration for recovery. Use a unique owner password and a password manager. The security panel states these limits explicitly and does not describe the application as certified or guarantee notification delivery.


## Staff credentials and employment changes

Open **Courts → Manage court → New staff login**. Enter a unique staff username and select Case manager or Coordinator, then **Create staff account**. Repeat for each staff member. Give each person an individual login rather than sharing credentials or repurposing a departing employee’s identity. Both roles currently manage participant access within their assigned court.

The owner sees the generated temporary password once, with the exact staff alias, court selection and `/admin` destination. Reveal/copy are explicit; credentials stay only in component memory and clear on dismissal, relevant navigation, court/account change, sign-out, or after five minutes. Lost handoffs require a new reset; passwords cannot be retrieved. The API does not accept caller-selected staff passwords, email addresses, owner claims, or arbitrary metadata, and never writes passwords to court audit events.

**Reset password for [username]** first restricts court operations in PostgreSQL, then changes the Auth password. Staff must prove the current temporary password and choose a different private password before court access resumes. The server uses an isolated, non-persistent Auth client for proof; it does not trust an old browser session as proof of the temporary password. Completion uses a credential version check, so concurrent revocation or a newer reset cannot be undone. A short operation lease prevents overlapping owner credential writes; failed resets stay restricted and can be retried. After setup, staff sign in again with their private password. Sessions created before a credential issue/reset are rejected for subsequent protected court API requests, even after setup completes.

For a departure, use **Revoke access for [username]**. Active membership is checked on protected requests; revocation blocks subsequent court operations while retaining the Auth identity, revoked assignment, actor/subject IDs and all existing audit events. It does not delete participant records or erase data already viewed or copied. Other staff accounts remain active. **View audit history for [username]** reads persisted events performed by or affecting that identity, including revoked accounts, with pagination for older events; participant private content and passwords are excluded. For a return, **Restore access** reactivates that same assignment and appends an event; reset its password if confidentiality is uncertain. Create a new identity for a replacement employee to keep attribution accurate.

The additive `owner_staff_credentials` migration preserves existing staff behavior and introduces rotation state, service-only credential/session operations, narrow private Auth lookups, and the required-password check in participant assignment/transition RPCs. Browser roles receive no new table or RPC grants. Existing accounts are not reset, revoked, or promoted by deployment. UI fixtures cover multiple staff, credential handoff, reset cancellation, sign-out races and retained revoked history; disposable PostgreSQL tests cover actual authorization, reset-version races, independent memberships and audit retention. Neither is evidence of production Auth delivery.
